# Phase G5.2 — Gate Evaluation

**Date:** 2026-08-30
**Scope:** [#191](https://github.com/voltron-1/Adversary-in-a-box/issues/191) (G5.2), gated on [#168](https://github.com/voltron-1/Adversary-in-a-box/issues/168) (G0.1) per `docs/20260813-remediation-plan.md` → Phase 5:

> **G5.2 — gated on G0.1.** If checksum offload is confirmed to kill app-layer rules: disable checksum validation, broaden `HTTP_PORTS`, enable double-decode.

## Evaluating the gate

G0.1's findings (`findings/20260813-runtime-confirmation.md`, Q1) are the authoritative source here:

- The configured setting is confirmed: `blue-team/detection/suricata/suricata.yaml:118` sets `checksum-validation: yes`.
- The invalid-checksum *counter* (whether packets are actually being discarded because of it) came back inconclusive — not because of contrary evidence, but because the stats-log probe used to check it was itself unable to produce a signal either way.
- Critically, Q1 also records **positive evidence against the premise**: "the full kill-chain integration test (`tests/integration/test_killchain.py`) passed with Suricata alerting correctly on every registered technique in every successful dispatch, which is strong indirect evidence checksum validation is not silently discarding real traffic in this environment."
- G5.1's own pcap-replay harness (`tests/test_suricata_pcap_replay.py`, this same phase) adds further evidence in the same direction: every app-layer rule case (HTTP, SMTP, SSH, SMB) that should fire against correctly-checksummed synthetic traffic does fire, with `checksum-validation: yes` in effect via the lab's own `suricata.yaml`. The two rules confirmed broken by that harness (sid:1000022, sid:1000050) are wrong-sticky-buffer / wrong-offset bugs (G5.4, unrelated to checksums), not app-layer rules failing to fire for a checksum reason.

**Gate condition:** *"If checksum offload is confirmed to kill app-layer rules"* — not met. No dispatch, in this spike or since, has produced evidence of app-layer rules failing to fire because of checksum validation. The available evidence points the other way.

## Disposition

No code change. Making G5.2's proposed changes (disabling `checksum-validation`, broadening `HTTP_PORTS` beyond the lab's own port 80, enabling `double-decode-path`/`double-decode-query`) without a confirmed problem would trade away real defensive value for no demonstrated gain:

- Disabling checksum validation stops Suricata from silently accepting a packet with a corrupted payload as if it were the real one — an actual detection-evasion vector on a network where nothing should be corrupting packets in the first place (the lab's own `internal: true` networks).
- Broadening `HTTP_PORTS` beyond port 80 (the only port the lab's `victim-web` service listens on) widens the app-layer HTTP parser's attack surface for no coverage gain in this lab topology.
- Enabling double-decode has a real false-positive/evasion-surface cost of its own and is normally recommended specifically to counter double-encoding evasion — a technique no red-team campaign in this lab currently uses.

If a future change to this lab's own traffic patterns (e.g. `victim-web` gaining a second HTTP port, or a campaign starting to rely on checksum-offload NIC behavior that this environment doesn't currently exhibit) produces real evidence the gate condition is met, G5.2 should be reopened against that evidence rather than implemented speculatively now.

Closes #191.
